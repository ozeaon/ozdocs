# Change request docs: old vs new

Comparing `change-requests.md` (existing) against `Change request registry.md` (new).

| #   | Topic                             | Old (`change-requests.md`)                                                                                                                                   | New (`Change request registry.md`)                                                                        |
| --- | --------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------- |
| 1   | When a change request is required | Only after column 6, Design Done. Adjustments in columns 4–5 don't need one.                                                                                 | Silent on threshold. "No exceptions" reads as covering all changes, including in-flight design work.      |
| 2   | Bugs                              | First-class category. External bugs via Google Form; internal bugs via BA/PM. Dev/design chat reports are ignored.                                           | Not mentioned at all.                                                                                     |
| 3   | Internal feedback triage          | Joseph and stakeholders route through BA/PM, who filter before anything reaches dev/design.                                                                  | Missing. Joseph appears directly as decision-maker in step 4.                                             |
| 4   | Priority framework                | None.                                                                                                                                                        | Formal Critical / High / Medium / Low table. Critical and High skip the Decide step.                      |
| 5   | Decision gate                     | BA and PM sign off for small design changes.                                                                                                                 | 4 outcomes (Approved / On Hold / Rejected / Needs More Info), owned by Joseph. PM sign-off removed.       |
| 6   | Dev-initiated changes             | Two flavours: **Dev-notified** (change already made, ticket for the record) and **Dev-blocked** (spec/design mismatch).                                      | Only **Dev-blocked** survives. Retroactive "record it after the fact" path is dropped.                    |
| 7   | Order of spec vs Figma update     | BA updates spec → PM signs off/assigns dev → Designer updates developer-facing Figma. Ticket returns to Ready for Dev only once spec and design are aligned. | BA moves ticket to "Create Dev Ticket" **before** Designer updates Figma. PM sign-off gone.               |
| 8   | "New idea" routing                | New features go through discovery (BRD → design/spec loop → signoff) per `new-feature-process.md`, or enter at Ready for Design (column 1).                  | Routes new idea to "Spec Pending" - a mid-design-track column that requires a signed-off design to enter. |
| 9   | Column name                       | "Create Dev Tickets" (plural) per `kanban.md`.                                                                                                               | "Create Dev Ticket" (singular).                                                                           |
| 10  | Assignee                          | Design-change tickets assigned to **BA and Designer**.                                                                                                       | **BA is the assignee** on every change request.                                                           |
| 11  | Change registry spreadsheet       | Not referenced.                                                                                                                                              | Mandatory log in Google Sheet for any code-touching change. New requirement, not a direct conflict.       |
